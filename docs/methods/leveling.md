# 采购计划均衡：削峰要有边界

<!--@include: @/snippets/methods-note.md-->

客户订单和销售预测经常一波一波来。供应商的产线更希望每周差不多。采购计划均衡，就是在这两者中间把下单摊开：少一点月底扎堆，少一点临时加急，也少一点因为怕缺料而一次下完。

摊开这件事有边界。过了边界，系统里的计划会变好看，产线却在等料，或者仓库堆着用不到的货。

## 高峰不要从系统里消失

真实需求是客户哪一周要提货、产线哪一周要上线。均衡只改变「我们哪一周向供应商买」，不改变「哪一周必须有货」。

系统里要同时留两列数：原始需求，和均衡之后的下单。只留均衡结果，后面没人知道高峰被藏起来了。销售还在按原来的出货日承诺，计划已经把那一周的需求挪走了。

::: scenario
一家做家电控制板的工厂，客户要在季度最后一周提走大约四周的货。计划员为了让采购订单好看，把这四周用量平均摊到后面四周。供应商的到货也跟着摊开。最后一周来提货时，仓库里只有大约四分之一。客户的出货日没有变，变的只是系统里的计划。四周、四分之一都是假设，用来说明这种改法会缺货。
:::

## 摊开之后，每一周仍然要盖住上线

均衡后的到货计划，要盖住每一周的真实上线需求。盖不住，就不是削峰，是把需求藏起来。

能做的通常只有两类：

- 高峰之前，供应商还没排满的几周，把能提前买的买进来。
- 提前买不进来的部分，在客户还来得及改出货日的时候告诉销售，而不是把需求改小。

供应商一周能稳定交多少，不要用对方销售口头说的「能赶」。用过去实际收进仓库的数量来估。算法写在 [供应商交期跟踪](./delivery-tracking)：稳定周量看正常周的中位数，红线周量看靠前的高位。超过红线还按原交期承诺，历史上就经常迟到。

::: scenario
假设某颗料过去正常周的入库中位数是每周 1 万只，大约九成的周不超过 1.2 万只。客户有一周要 4 万只。把 4 万只做成一张要求下周交货的订单，不会让供应商在一周里变出 4 万只的能力。能做的是：从高峰往前看，还有几周没到 1 万只，就先把那些周补到接近 1.2 万只；剩下补不齐的，算给销售听。1 万、1.2 万、4 万都是假设。
:::

## 起订量会挡住「每周都一样」

MOQ（最小起订量）是供应商肯单独生产或单独发货的最少数量。真实用量低于起订量时，硬把每周都下成同样的小数，订单会接不住。

这时的均衡是「批与批之间大致均匀」，不是「每一周都有一行订单」。两周或三周合一批，只要到货日仍然盖住中间每一周的上线，就还在边界里面。合批会多压几天库存，这笔库存要有上限，不能为了凑整箱把一个季度都买进来。

::: scenario
假设每周真实上线要用 3000 只，供应商起订量是 10000 只。每周下一张 3000 的订单，供应商不受理。每三周合一批 10000，比一次性买 30000 更接近真实消耗。前提是仓库放得下多出来的几天，而且这 10000 只在接下来三周里确实会用掉。数字是假设。
:::

## 提前买，是用钱和库位换平稳

为了削掉高峰而提前买，货会先占仓库和应付账款。边界是事先写清的金额或周数，不是「供应商说能做我们就都收」。

电子料处在涨价段时，提前买还有价格风险：买早了可能避开缺货，也可能买在高位。品类文章里的原则是，只对交期长、来源单一、停线影响大的料多备，并且写下退出条件。见 [实战打法](/categories/electronics/playbook)。那是电子料的判断，换到钢材或塑料，约束不同，这篇只保留「要有上限」这一条。

## 下单之前对一下这四句

1. 原始需求还在，没有被均衡结果覆盖掉。
2. 均衡后的到货，仍然盖住每一周要上线的数量。
3. 没有任何一周的计划到货，超过供应商的红线周量却还写着正常交期。
4. 为了起订量多买的部分，有数量上限，也有预计用完的日期。

四句都答得出，这张计划才算削过峰。少一句，就还是一张改过日期的需求。
